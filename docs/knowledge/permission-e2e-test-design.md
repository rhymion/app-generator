# Permission E2E Test Design — Four Groups (cmd_518/cmd_520)

## Background

cmd_511/cmd_515/cmd_516 fixed several permission and org-isolation gaps in the generated app
(cross-entity read graceful degradation, org-scope save-path validation, FK read-permission
UI degradation). cmd_518 designed a four-group test taxonomy to close the remaining permission
E2E coverage gaps those fixes left untested. cmd_520 batch A implements Group 0 (generic CRUD/
import/export permission denial) and Group 3 (cross-organization isolation) — both independent
of cmd_516 and generated by `test_api_spec.cy.ts.jinja2`. Batch B (Groups 1/2 — UI-visible FK
read-permission behavior, dependent on cmd_516) is tracked separately.

## Group 0: generic permission denial (7.3–7.6)

Extends the existing `describe('Permission errors', ...)` block (7.1 GET list, 7.2 POST — both
pre-existing) with:

- **7.3** — PUT denied (`{% if can_edit %}`)
- **7.4** — DELETE denied (`{% if can_delete %}`)
- **7.5** — GET export denied (`{% if can_list and can_export %}`)
- **7.6** — POST import denied (`{% if import_eligible %}`)

### 7.5/7.6 use session auth, not X-API-Key — a correction from the original design sketch

The original cmd_518 design doc sketched 7.5/7.6 using `db:createLimitedApiUser` +
`X-API-Key`, mirroring 7.1–7.4. That assumption doesn't hold: `api_export_route.ts.jinja2` and
`api_import_route.ts.jinja2` resolve the actor exclusively via `getSessionUserId()`
(`lib/authz.ts`) — they never read `X-API-Key` at all. A request with only an API-key header has
no session, so `getModelPermissions()` falls back to an unauthenticated/empty-permission result
and the route rejects with 401 or 403 regardless of what permissions the API-key-bearing user
actually holds — the test would pass but wouldn't be testing what it claims to test (it would
be indistinguishable from testing "no key = 401").

7.5/7.6 therefore use `db:createSessionUserWithPermission` (an existing helper, already used by
`cypress/e2e/api/import_batch2.cy.ts`) + `cy.login(email, TEST_CREDENTIALS.password)` to get a
real session cookie for a user with `{}` (all-false) permissions on the entity. This mirrors the
mechanism the pre-existing `import_batch2.cy.ts` custom spec already used for the same reason.

## Group 3: cross-organization isolation (G3)

New `describe('Cross-organization isolation (G3)', ...)` block, gated on
`{% if should_filter_by_org %}` (only entities with an `organization_id` FK):

- **G3.1** — POST with a foreign `organization_id` in the body is rejected (`{% if can_new %}`).
  Asserts `status >= 400` only (not an exact code): the underlying `service.ts.jinja2`
  `throw new Error('Organization access denied')` isn't wrapped in `ApiError`, so
  `handleApiError()` currently falls through to a generic 500 rather than 400/403. That's a
  pre-existing API-quality gap, out of scope for this cmd — see the comment at the assertion.
- **G3.2** — GET on a row in a foreign org returns 404, not 403 (existence hidden) (`{% if can_view %}`).
- **G3.3** — PUT on a row in a foreign org returns 404 (`{% if can_edit %}`).

All three use the default `TEST_API_KEY` (the main test user), who `db:createCrossOrgScenario`
enrolls in orgA only — so these tests exercise a *permitted, same-org-capable* actor reaching
across an org boundary, not just an unauthenticated/unpermitted one.

### `db:createCrossOrgScenario` — generic by construction, not by re-deriving FK logic

`cypress/support/db-helpers.ts` (`test_db_helpers.ts.jinja2`) gains
`createCrossOrgScenario(entityName, entityId?)`, registered as a cypress task directly in
`cypress.config.ts` — **not** in the auto-generated `test_tasks_registry.ts.jinja2**, which only
carries per-entity `db:populate<Entity>*` tasks. The original design doc listed the wrong file
for this registration; `db:createLimitedApiUser`, `db:createSessionUserWithPermission`, and
`db:createApiUserWithPermission` are the existing precedent for exactly this — general-purpose,
non-per-entity cypress tasks live hand-wired in `cypress.config.ts`.

The helper itself is deliberately generic: rather than re-deriving each entity's full
required-field/FK-dependency construction logic (already implemented per-entity in
`populate<Entity>Data()`), the generated spec creates a normal row first via
`db:populate<Entity>` and passes its id to `createCrossOrgScenario`, which does one generic,
entity-agnostic step — a raw `(prisma as Record<string, any>)[entityName].update()` reassigning
that row's `organization_id` to a freshly created "foreign" org. This deliberately bypasses the
service layer's own org-membership validation; constructing a "row in an org the actor isn't a
member of" fixture is the entire point, so going around that validation for fixture setup is
correct, not a defect. `entityName` must equal the Prisma model name (true for every
`should_filter_by_org` entity in the default schema — no base/`_detail` split entity currently
carries `organization_id`).

`org_cross_post_body` (new `api_spec_context()` context var) reuses the existing
`_post_body_impl(skip_field, indent)` helper (already used for `i7_post_body` /
`post_body_missing_field`), skipping `organization_id` so the generated G3.1 test can inject its
own foreign value.

## FK Permission / Cross-org coverage comment

Every generated `cypress/e2e/api/<entity>.cy.ts` now carries a one-line comment near the top
(`// FK Permission / Cross-org Test Coverage (cmd_520 batch A): 7.3=... 7.4=... 7.5=... 7.6=...
G3=...`) recording which of the five new test groups were actually generated for that entity and
why (or why not) — so "covered" claims can be verified by `grep` against real generated output
instead of assumed from the template diff alone. In the default `app-generator` schema, **no**
entity has `organization_id` — G3/N3 both generate zero instances there; consumer apps that add
an org-scoped entity are the first place either actually renders. This was verified directly by
rendering `test_api_spec.cy.ts.jinja2` against a synthetic org-scoped entity (see cmd_520's
report for the entity fixture and rendered output).

## CSV import dotted-FK org filter gap (cmd_515, tracked separately — OQ-2)

`api_import_route.ts.jinja2`'s dotted-FK lookup (`prisma.<lookup_entity>.findMany({ where: {
<lookup_field>: <csv value> } })`) is not scoped by the actor's organization: a natural-key value
that collides across organizations can resolve to a row outside the actor's org. cmd_520
deliberately does **not** add a test asserting the (currently incorrect) org-filtered behavior —
a permanently-red test would violate the SKIP=FAIL spirit and effectively freeze the bug as
intended behavior. Instead, a `// TODO(cmd_515 dotted FK org filter gap...)` comment is emitted
directly in the generated route (gated on `should_filter_by_org`, appearing in every consumer's
`app/api/<entity>/import/route.ts` that has both a dotted FK import key and org scoping) pointing
at this doc. Fix belongs in the separate cmd that scopes that `findMany()` by `organization_id`.
