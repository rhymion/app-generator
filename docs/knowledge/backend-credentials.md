# Credentials a generated app uses to reach its backends

This page lists the long-lived credentials the application and its deploy scripts use to authenticate to the
database, Redis and the scheduled-task caller; says what a leak of each one allows; and records which credentials
already avoid stored secrets. It describes the code in this repository. The destinations themselves are listed in
`outbound-communications.md`, and the key material derived from `AUTH_SECRET` in
`cryptographic-inventory-and-key-management.md`.

## Static credentials

| Credential | What it authenticates | Where it is stored | What the app does with it |
|------------|-----------------------|--------------------|---------------------------|
| `DATABASE_URL` (password inside the URL) | The application's PostgreSQL connection. On Vercel it is the pooled endpoint of the database host, and an app that runs as the restricted `audit_log` role uses that role's URL (`audit-log-append-only.md`). | Sensitive Vercel variable (`scripts/vercel-env.sh`); Secret Manager secret `app-database-url` on GCP (`scripts/gcp-setup.sh`, mounted by `scripts/gcp-deploy.sh`); `.env*` files for local use | Passed to Prisma by the running app. |
| `DIRECT_URL` (password inside the URL) | The owner connection used by migrations only | Sensitive Vercel variable; Secret Manager secret `app-direct-database-url` on GCP | Read by the Prisma CLI through `prisma.config.ts` (it wins over `DATABASE_URL` there) for migrations; the GCP migration Job mounts it (`scripts/gcp-deploy.sh`). The running service does not need it. |
| `REDIS_URL` (password inside the URL) | The rate-limit store (`lib/rate-limit/redis.ts`). Optional: without it the limiter keeps its counters in memory per instance. | Sensitive Vercel variable; Secret Manager secret `app-redis-url` on GCP | Passed to the Redis client. A Redis outage is handled by falling back to the in-memory limiter (`authentication.md`). |
| `CRON_SECRET` | The caller of `/api/scheduled-tasks/*`: Vercel Cron sends it as `Authorization: Bearer`, and a Cloud Scheduler job is given the same header by hand (`scheduled-task-operations.md`) | Sensitive Vercel variable (`CRON_SECRET`, and `CRON_SECRET_STAGING` for Preview); Secret Manager secret `app-cron-secret` on GCP | Compared with `lib/_secret_compare.ts` (SHA-256 of both sides, then `timingSafeEqual`). |

None of these is generated by the application. The deploy scripts create the database and Redis credentials through
the providers' APIs or accept them from `.env.production.local`, and generate `CRON_SECRET` once.

## What a leak allows

- **`DATABASE_URL`** gives whoever holds it the privileges of the role in the URL, from anywhere the database accepts
  connections. The restricted `audit_log` role can add rows to the audit log but not change or delete them, and has the application's usual rights on other tables; any other role the
  operator puts in the URL has the privileges the operator granted it. `DIRECT_URL` is the owner of the schema and can
  do anything to the data.
- **`REDIS_URL`** lets the holder read and write the rate-limit counters, so it can reset or exhaust any user's or
  address's budget. No session, token or application data is stored in that Redis.
- **`CRON_SECRET`** lets the holder run any scheduled task now, on its own schedule, as the scheduled-task system actor
  (`scheduled-task-operations.md`). It does not give a session, an API key or access to any other route.

## Credentials that are already short-lived or keyless

- **Cloud Storage on Cloud Run** (attachments and audit-log copies) uses Application Default Credentials, which on
  Cloud Run is the service account attached to the service or Job. No key file is stored.
- **Audit-log copies on Vercel** can use `AUDIT_LOG_GCS_AUTH=vercel-oidc`: the Vercel OIDC token is exchanged for
  short-lived Google credentials through Workload Identity Federation, and the `GCP_*` variables are identifiers, not
  secrets (`audit-log-append-only.md`).

The attachment backends that read a token (`ATTACHMENT_BLOB_READ_WRITE_TOKEN`, `BLOB_READ_WRITE_TOKEN`) and the audit-log
S3 backend are outside this page's three subjects.

## Evaluation

| Credential | Short-lived or per-service alternative | Finding |
|------------|----------------------------------------|---------|
| `DATABASE_URL` | A token that the platform exchanges for a database login (workload identity, IAM database authentication) | The app has no code path for it. Prisma receives one connection string, and the string is built once at deploy time. Using a token would need a connection layer that refreshes the password before it expires, on every platform and pooler in use. Whether the current database hosts support token login is not verified here; check the provider documentation before designing it. Today the control is the narrower role: use the restricted role in `DATABASE_URL` and keep `DIRECT_URL` out of the running service. |
| `REDIS_URL` | A per-service credential or token | The app reads one URL. The Redis holds counters only, and the limiter works without it, so the impact of a leak is bounded as described above. Rotating the password is the available control. |
| `CRON_SECRET` | A signed identity token from the scheduler instead of a shared bearer secret | Vercel Cron sends the bearer secret and offers no alternative; a Cloud Scheduler job can send an OIDC token, but the route does not verify one. A leak is bounded as described above. Rotation is the available control. |

## Rotation

The app accepts one value of each credential, so a rotation replaces the value in the secret store and redeploys.

- **Database or Redis password:** change it at the provider, update the Vercel variable or the Secret Manager secret
  (`scripts/vercel-env.sh`, `scripts/gcp-setup.sh`), and redeploy so every instance reconnects. Existing pooled
  connections keep working until they are closed, so expect a short overlap.
- **`CRON_SECRET`:** change the variable, then update every caller that sends it. On GCP that is each Cloud Scheduler
  job's `Authorization` header, because the jobs are created by hand and the scripts do not update them. Until a caller is
  updated its requests get `401`, which appears in the logs.

## Status

The credentials above stay static in this release. The coverage rows are V13.2.1 (this page) and V13.2.2 (the restricted
database role). Token-based database login and a verified scheduler identity would change the connection layer and the route's
authentication; this page does not specify them.
