# External services: security contracts

One row per external service the generator integrates with. A change that adds an integration, or changes how an existing one behaves when misconfigured, must add or update its row in the same pull request.

Versions below are the ones locked in `package-lock.json` when the page was written; check the lock file for the current value. "Primary source" names where the SDK behavior was read, not a summary of someone else's description.

| Service | Public or private, who can read | Credential: scope and lifetime | Wrong configuration or leaked credential | Fails open or closed | Primary source |
|---|---|---|---|---|---|
| Google Cloud Storage (attachments, `lib/attachment/storage.ts`) | Private. Objects are saved without an ACL under uniform bucket-level access; the route authorizes first and streams the object, so no signed URL leaves the server. | Application Default Credentials: the Cloud Run service account holds `roles/storage.objectUser` on the one bucket. No key file is stored. Token lifetime is set by Google. | A bucket that allows public access would expose objects, but keys are opaque UUIDs and `scripts/gcp-deploy.sh` warns when uniform bucket-level access or Public Access Prevention is off. A leaked service-account token reaches the one bucket only. | Closed: with no bucket and no other backend configured on an ephemeral platform, `storageBackend()` throws instead of writing to local disk. | `@google-cloud/storage` 8.4.0; `docs/knowledge/attachment-storage.md` |
| Vercel Blob (attachments) | Private (`access: 'private'`). The route streams the object after authorizing. | `ATTACHMENT_BLOB_READ_WRITE_TOKEN`, `BLOB_STORE_ID` (short-lived Vercel OIDC token) or `BLOB_READ_WRITE_TOKEN`, resolved once by `blobTarget()`. A read-write token is long-lived and covers the whole store. | A leaked read-write token allows reading, replacing and deleting every object in that store; rotate it and re-point `ATTACHMENT_BLOB_READ_WRITE_TOKEN`. The wrong store is never picked silently because the store is passed explicitly to every call. | Closed on a missing credential (see Google Cloud Storage). | `@vercel/blob` 2.8.2; `docs/knowledge/attachment-storage.md` |
| Local disk (attachments, no bucket and no Blob credential) | Private to the host. Written under `.uploads/` or `ATTACHMENT_LOCAL_DIR`, never under `public/`. | None; file-system permissions of the process. | Pointing `ATTACHMENT_LOCAL_DIR` into a served directory would publish files; the default never does. | Closed on ephemeral platforms (throws). Open on a developer machine by design: it is the local default. | `lib/attachment/storage.ts`; `docs/knowledge/attachment-storage.md` |
| Redis / Upstash (rate limiting, `lib/rate-limit/redis.ts`) | Private, reached over `REDIS_URL`. Holds only counters keyed `rl:<bucket>:<key>`; no user data. | The password inside `REDIS_URL`; no expiry unless the provider rotates it. | A missing `REDIS_URL` selects the per-process in-memory limiter. An unreachable or erroring Redis drops to the same in-memory limiter and logs `[rate-limit:fail_open]`. A hosted production deployment refuses a Redis URL without TLS (`lib/transport-security.ts`). | **Open, by decision** (Issue #587): the limiter is a defensive gate in front of authentication, so availability outweighs the lost cross-instance protection. The per-process fallback still limits each instance (Issue #1178). | `ioredis` 6.0.0; the comment above the fail-open branch in `lib/rate-limit/redis.ts` |
| Stripe (`x-payment`, `code_generator/templates/payment_stripe_client.ts.jinja2`, `POST /api/webhooks/stripe`) | Stripe holds card data; the app never sees it. The app stores the payment state of its own records. | `STRIPE_SECRET_KEY` (a live key starts with `sk_live_`) and `STRIPE_WEBHOOK_SECRET` (verifies event signatures). Both are long-lived until rotated in the Stripe Dashboard. | A missing secret key fails at the first Stripe call. A missing webhook secret makes the webhook route throw before any event is processed. A request without a `stripe-signature` header is answered `400`. The fake Stripe client is refused in production. A leaked secret key can create charges and refunds; roll it in the Dashboard. | Closed. | `stripe` 23.0.1; `docs/knowledge/stripe-payment-integration.md` |
| Google OAuth (`auth.ts`, Auth.js Google provider) | Google holds the account. The app receives the profile the default scopes allow (the provider is configured with `prompt: select_account` and no extra scope). | `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, long-lived until rotated in the Google Cloud console. Registered only when both are set and the site configuration lists `google`. | An unset id or secret leaves the provider unregistered, so only Credentials sign-in works. A Google account is identified by its `sub`, never by email, so an address re-created at Google does not take over an existing user. An allow-list of domains (`isDomainAllowed`) can restrict who signs in. A leaked client secret lets another party run the OAuth flow as this app; rotate it. | Closed: no provider, no Google sign-in. | `next-auth` 5.0.0-beta.32 (`@auth/core`); `docs/knowledge/authentication.md` |
| Database and connection pooler (`DATABASE_URL`, optional `PRISMA_DATABASE_URL`) | Private. Holds all application data. | The database role's password in the URL. `PRISMA_DATABASE_URL` (Prisma Accelerate) is unset by default. | On a hosted production deployment (`NODE_ENV=production` with `K_SERVICE` or `VERCEL`) startup refuses a connection string that does not ask for TLS and is not a Unix socket (`lib/transport-security.ts`). Local development and the e2e gates stay on plain connections. A leaked URL gives full database access; rotate the role password. | Closed in hosted production (startup fails). Open in local development by design. | `@prisma/client` 7.10.1, `pg` 8.23.1; `lib/transport-security.ts`; `docs/knowledge/DATABASE_QUICK_REF.md` |
| Scheduled-job runners (Vercel Cron, Cloud Scheduler; `POST /api/scheduled-tasks/<task>`) | The route is not public: it needs `CRON_SECRET` or a signed-in caller with the `ScheduledTaskRunner` role. | `CRON_SECRET`, compared in constant time with `Authorization: Bearer <value>`; long-lived until rotated. Production and Preview use different values. | With `CRON_SECRET` unset the route falls back to the role check, so an unauthenticated cron request gets `401` and the schedule stops firing; nothing runs unauthenticated. A leaked secret lets the holder run any scheduled task now; rotate it. | Closed. | `code_generator/templates/scheduled_task_route.ts.jinja2`; `docs/knowledge/scheduled-task-operations.md` |
| Workload identity federation (audit-log storage, `lib/audit-log-integrity/storage-gcs.ts`) | The audit-log bucket is private. | With `AUDIT_LOG_GCS_AUTH=vercel-oidc` a Vercel OIDC token is exchanged through Google Security Token Service for short-lived credentials of one service account; no key is stored. `adc` (the default) uses the attached service account. | A missing `GCP_*` variable throws, naming the variable. A wrong `AUDIT_LOG_GCS_AUTH` value throws. A leaked OIDC token is short-lived and limited to the pool and provider it was minted for. | Closed. | `google-auth-library` 11.3.1, `@vercel/oidc` 4.0.3; <https://vercel.com/docs/oidc/gcp> |

## Fail-open integrations

There is one: the Redis rate limiter. It fails open because a Redis outage must not take sign-in down with it (Issue #587), and the failure is never silent: every failure is logged as `[rate-limit:fail_open]` and the per-process limiter keeps applying the same buckets. Local disk for attachments and plain database connections are permissive only outside hosted production.

## Adding an integration

Add a row with all five fields before the integration merges: who can read the data, the credential's scope and lifetime, what happens when configuration is wrong or the credential leaks, whether it fails open or closed, and the primary source with a version. A fail-open choice needs the reason and a link to the Issue or decision, as above.
