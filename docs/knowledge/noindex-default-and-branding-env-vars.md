# Default noindex, and title/copyright branding env vars

**Status: Implemented**
**Date: 2026-08-22**

## Scope decision

Generated apps are primarily internal tools, not public-facing products. A
consumer who deploys one to Vercel gets a real production URL — and unlike
Vercel preview deployments, production deployments receive no automatic
`X-Robots-Tag: noindex` protection (see
[Vercel: managing crawlers](https://vercel.com/docs/bots/managing-crawlers)).
Without an explicit opt-out, an internal tool's data (entity lists, record
detail pages) is exactly as indexable as a public marketing site.

The generator now ships every app with search-engine indexing blocked by
default. A consumer who *wants* their deployment indexed sets one boolean to
opt back in.

## Mechanism: metadata, not `robots.txt`

`app/robots.ts` (a `Disallow` rule in `/robots.txt`) was considered and
rejected. `Disallow` tells crawlers not to *fetch* a page at all — a crawler
that never fetches the page never sees a `noindex` meta tag on it either.
Google's own guidance is to `allow` the page and rely on `noindex` instead;
`Disallow` can leave a URL indexed with no snippet, which is worse than not
using either mechanism (see
[Next.js: Metadata robots field](https://nextjs.org/docs/app/api-reference/functions/generate-metadata#robots),
[Next.js: robots.ts file convention](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots)).

So indexing control here is entirely `<meta name="robots">`, set via
`app/layout.tsx`'s `Metadata.robots` field:

```ts
const noindex = siteConfig.seo?.noindex ?? true;

export const metadata: Metadata = {
  title: siteConfig.title,
  description: 'Application generated by auto-generation code',
  ...(noindex && {
    robots: {
      index: false,
      follow: true,
      googleBot: { index: false, follow: true },
    },
  }),
};
```

`app/layout.tsx` only *reads* `siteConfig` — it never needs to be
hand-edited, so a re-run of `generate-code` can't clobber a consumer's
choice.

## The default is `true`, and stays `true` if the setting disappears

`lib/site-config.ts` (append-only, consumer-owned — never overwritten by
`cleanup.py`/`generate-code`) ships with:

```ts
seo: {
  noindex: true,
} as { noindex?: boolean },
```

The `?? true` fallback in `app/layout.tsx` means the *absence* of a value —
whether the whole `seo` block is deleted, or just `noindex` inside it — is
indistinguishable from an explicit `noindex: true`. This is the opposite of
a naive `siteConfig.seo?.noindex && {...}` read, which would treat a missing
field as "not set, so indexed." Verified empirically both directions with a
local dev build:

- Default (`seo: { noindex: true }`, or `seo` omitted entirely, or
  `noindex` omitted): rendered HTML includes
  `<meta name="robots" content="noindex, follow"/>`.
- `seo: { noindex: false }`: no `robots` meta tag is emitted at all —
  the page is indexable, per Next.js's normal (no-`robots`-field) behavior.

To allow indexing, a consumer sets `noindex: false` in their own
`lib/site-config.ts` — a one-line, one-file change.

## Why not a schema annotation

`x-payment`/`x-cloud`-style schema annotations are per-entity or per-app
generation-time switches read by `code_generator/generate.py`. Indexing
control isn't a code-generation concern — it doesn't change what gets
generated, only a runtime `<meta>` tag — so it belongs in the same
consumer-owned settings file as `title`, `auth`, and `navLinks`, not in
`json_schema.yaml`.

## Consumer impact (proj_c / proj_g / proj_h)

None of the three known consumer checkouts (`app-template`,
`app-template-4`/inventory-app, `app-template-5`/insurance-app) carry their
own customized `lib/site-config.ts` locally — each gets this file only
through the `app-generator` submodule, so none currently declare an
explicit `seo.noindex` override to reconcile. None are known or documented
as public-facing/marketing deployments (all three are private GitHub repos;
insurance-app in particular is a demo rebuild in progress that this task
did not touch, read-only). The default flip is therefore safe for all three
as they stand today. If any of them is later deployed somewhere that wants
search-engine visibility, that deployment sets `noindex: false` in its own
`lib/site-config.ts`.

## `NEXT_PUBLIC_APP_TITLE` / `NEXT_PUBLIC_APP_COPYRIGHT` (demo branch fold-in)

Folded in alongside the noindex work, from a hand-maintained local branch
(never pushed to `origin`) that customized branding for a specific demo
deployment:

```ts
title: process.env.NEXT_PUBLIC_APP_TITLE || "Generated by App Generator",
...
copyright: process.env.NEXT_PUBLIC_APP_COPYRIGHT || "Copyright © 2026 Rhymion Labs. All Rights Reserved.",
```

Two changes from the original demo branch, both to close a silent-break
risk rather than just for style:

1. **Both vars are now `NEXT_PUBLIC_`-prefixed.** The original branch used
   bare `COPYRIGHT` for the footer. `app/[locale]/@footer/page.tsx` is
   currently a Server Component, so a bare env var reads fine today — but
   if it's ever converted to a Client Component, a bare (non-`NEXT_PUBLIC_`)
   var silently reads as `undefined` on the client with no build error and
   no runtime exception; the footer would just quietly fall back to the
   default text. Prefixing both the same way removes that trap.
2. **`copyright` moved into `siteConfig`, alongside `title`.** The original
   branch left `copyright` as a footer-local `process.env` read (a ternary,
   `? … : "..."`) while `title` went through the already-central
   `lib/site-config.ts`. Consolidating both into `siteConfig` means every
   piece of app identity lives in one file, and the footer reads
   `siteConfig.copyright` — a plain `||` fallback, same shape as `title`,
   no ternary/template-string needed.

**Operationally important**: both vars are inlined into the client bundle
at *build* time (this is what `NEXT_PUBLIC_` means in Next.js — see
[Next.js: Environment Variables](https://nextjs.org/docs/app/guides/environment-variables)).
Changing either on Vercel requires a rebuild (redeploy the same build, or
push a new commit) — updating the Vercel dashboard env var alone has no
effect on an already-built deployment. Documented in `.env.example` and in
the inline comments on both `siteConfig` fields.
