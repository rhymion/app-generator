# `x-generate.invalidate` with no handler/module — write-once stub

**Status: Fixed**
**Date: 2026-08-06**

## Problem

`x-generate.invalidate` accepts either a bare bool or a dict
(`{enabled, handler, module}`). When enabled without a `module` (bare
`invalidate: true`, or the dict form with `handler`/`module` omitted), two
generated files disagreed on how to reach the fallback handler:

- `actions.ts.jinja2`'s "no module" branch never imported anything — it
  inlined a bare `throw new Error('invalidateX: handler not configured')`.
  The branch's own comment already named the intended target
  (`lib/{{ parent }}/invalidate_handler.ts`), but nothing wrote that file.
- `invalidate_action_route.ts.jinja2`'s "no module" branch unconditionally
  imported `invalidate{{ parent_pascal }}` from that exact path. Since
  `generate.py` never emitted the file, this import target never existed —
  `next build` fails the moment any entity takes this branch.

This repo's own `json_schema.yaml` has exactly one entity using
`invalidate` (`user`), and it always supplies an explicit `handler`/`module`
(`anonymizeUser` / `lib/compliance/anonymize_user`) — so the "no module"
branch had never actually been generated by any default-schema build. A
consumer (proj_c) hit it first when adding `invalidate` to a `location`
entity without wiring a handler, and got a build break with no actionable
error message.

## Fix

Write the missing file: when `can_invalidate` is true and `invalidate_module`
is empty, `generate.py` now emits a write-once stub at
`lib/{{ parent }}/invalidate_handler.ts` (via `_write_stub`, so a
hand-edited copy survives regeneration) exporting
`invalidate{{ parent_pascal }}(id): Promise<void>`, which throws a clear,
actionable error until a human implements real invalidate logic there (or
points `x-generate.invalidate.module`/`handler` elsewhere instead). This
mirrors the existing `service_after_create.ts`/`service_after_approve.ts`
stub convention already used for other "hand-written extension point"
mechanisms this generator cannot fill in generically.

`actions.ts.jinja2`'s "no module" branch now imports that same stub
(aliased — see below) and calls it instead of inlining the throw directly;
`invalidate_action_route.ts.jinja2`'s existing unconditional import now
resolves because the file actually exists.

**Aliasing note**: `actions.ts.jinja2` itself exports a wrapper function
also named `invalidate{{ parent_pascal }}` (the server action). Importing
the stub's export under its own name would collide with that wrapper inside
the same file — so the import is aliased
(`import { invalidateX as _invalidateXStub } from '...'`). This is the same
class of same-name collision documented in
`docs/knowledge/appendix/cmd564-location-invalidate-consumer-patch.md` for
consumer-supplied handlers; the generated stub avoids it structurally by
being imported only under an alias.

Also fixed in passing: `invalidate_action_route.ts.jinja2`'s route
docstring read "Anonymizes all PII for the given {{ parent }} record.
Irreversible." — `user`-specific wording baked into a generic template.
Generalized to "Invalidates the given {{ parent }} record via the
configured handler."

## Does this conflict with the earlier "plug-in point, not generic soft-delete" ruling?

Flagged for confirmation, not silently assumed: that earlier ruling deliberately treats
`invalidate` as a plug-in point — the generator does not auto-implement
domain behavior; `user` plugs in `anonymizeUser` by hand. The stub added
here does **not** implement any invalidate behavior (it only throws) — it
exists purely so generated code **builds**, with a loud, explicit runtime
failure and a pointer to what needs hand-implementing, exactly like the
already-established `service_after_create.ts`/`service_after_approve.ts`
stub pattern for other plug-in points. No default soft-delete semantics are
introduced. If this reasoning is wrong, this doc — not any generate.py
default value — is the marker to correct.

## Is a generic `invalidated_at` Prisma column achievable?

No, and this is not new/specific to `invalidate`: `prisma/schema.prisma`
per-entity models are hand-maintained by every consumer (see
`docs/knowledge/appendix/cmd564-location-invalidate-consumer-patch.md`
§1.2 and the equivalent `cmd562` id-FK consumer-migration doc) — the
generator's `json_schema.yaml` never derives Prisma schema content for
business entities. `invalidated_at` is one hand-added column among many;
no new gap was found by this investigation beyond the general convention.

## Verification

`code_generator/tests/fixtures/invalidate_gate/` gained a third fixture
entity, `sprocket` (`invalidate: true`, no handler/module — the
never-before-generated branch), alongside the existing `widget`
(with module) / `gadget` (no invalidate) pair from that earlier ruling.
`code_generator/tests/test_invalidate_mechanism_fixture.py` asserts:

- the stub file is written and exports `invalidateSprocket`
- `actions.ts` imports it under the aliased name and calls it
- the invalidate API route's unconditional import now resolves to a real
  file

Confirmed by re-running against the pre-fix `generate.py`/`actions.ts.jinja2`
(route template's import lines were already correct pre-fix, so only the
generator-side change was reverted for this check): the stub-exists and
actions.ts-imports-stub assertions failed (file missing / bare throw with no
import); the route-imports-stub assertion already passed, since that
template's unconditional import was correct all along — the missing piece
was only that `generate.py` never wrote the file it imports. All three pass
after the fix.

## Addendum: stub now branches on the actual `invalidated_at` column

The "does not implement any invalidate behavior (it only throws)" claim
above no longer holds unconditionally. A follow-up change to
`invalidate_handler_stub.ts.jinja2` (on `doreen/invalidate_stub`, ahead of
this doc) replaced the unconditional throw with an unconditional
`prisma.{{ model }}.update({ data: { invalidated_at: new Date() } })` —
useful as a real default for models that do carry that column, but a build
break (regression of the very problem this doc describes) for any
`can_invalidate` entity whose Prisma model doesn't.

`generate.py` now checks the entity's actual Prisma model (reusing the
`schema_deriver.parse_prisma_schema()` parse already done once per
`generate()` run for `set_prisma_uniques`, not a new parse) and passes
`has_invalidated_at_column` into the stub's render context:

- column present → the default `prisma.{{ model }}.update(...)` (the plug-in
  point still exists; a human may still replace it with domain logic)
- column absent → falls back to the original throw described above

Fixture coverage: `code_generator/tests/fixtures/invalidate_gate/` gained a
fourth entity, `cog` (`invalidate: true`, no handler/module, **no**
`invalidated_at` column), alongside `sprocket` (same config, but its model
**has** the column). `test_invalidate_mechanism_fixture.py` now asserts on
the stub file's actual body content for both — `sprocket` must contain the
update call and no throw, `cog` must contain the throw and no prisma call.
The original three assertions above only checked file existence and import
statements, never the body, which is why the regression this addendum fixes
wasn't caught by them.
