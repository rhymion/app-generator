# API e2e specs (`cypress/e2e/api/`)

This directory holds the REST API end-to-end specs. Some are generated by the
code generator; others are hand-written supplements. This file documents which
is which and **what you have to do when you add a new entity or need coverage
the generator doesn't produce**.

## File taxonomy

| File pattern | Origin | Overwritten by `generate-code`? | Edit by hand? |
|--------------|--------|-------------------------------|---------------|
| `<entity>.cy.ts` | Generated (`templates/test_api_spec.cy.ts.jinja2`) for entities with `x-generate.api: true` and `test: true` | **Yes** | No — changes are lost on regen |
| `<entity>_reservation_gen.cy.ts` | Generated (`templates/test_reservation_spec.cy.ts.jinja2`) for entities with an `x-reservation` **count** mode | **Yes** | No — changes are lost on regen |
| `<entity>_reservation.cy.ts` (no `_gen`) | **Hand-written** supplemental spec | No | Yes — this is yours |

The generated files carry an `// AUTO-GENERATED - DO NOT EDIT` header. The
matching generated helpers live under `cypress/support/<entity>/`:
- `helper.ts` and `reservation_gen_helper.ts` — generated
- their `db:*` tasks are auto-registered via `...getGeneratedTasks()` in
  `cypress.config.ts` (the list comes from the generated
  `cypress/support/generated-tasks.ts`).

## What the generator covers — and what it doesn't

For an `x-reservation` count-mode entity, `<entity>_reservation_gen.cy.ts`
covers the core paths: multi-item allocation, insufficient-stock rollback,
`criteria` compliance, and `policy.orderBy` ordering.

It does **not** cover scenario-specific edge cases such as true concurrency
(two simultaneous requests for the last unit) or the update/delete mutation
guards. Those go in a hand-written supplemental spec — see
`<entity>_reservation.cy.ts` for a worked example.

## Adding a hand-written supplemental spec

1. **Create the spec** at `cypress/e2e/api/<entity>_<topic>.cy.ts` (no `_gen`
   suffix — that suffix is reserved for generated files and would be
   overwritten).
2. **Import credentials with the correct relative path.** From
   `cypress/e2e/api/` the support dir is two levels up:
   ```ts
   import { TEST_API_KEY } from '../../support/test-credentials';
   ```
   (Do not deep-path back through the project root — it resolves outside the
   repo and fails to compile.)
3. **Put DB setup/assertion logic in a helper**, not inline, e.g.
   `cypress/support/<entity>/reservation_helper.ts` (note: no `_gen`).
4. **Register your `db:*` tasks** in `cypress.config.ts` under `on('task', {…})`,
   *after* the `...getGeneratedTasks()` spread:
   ```ts
   async 'db:seedReservationInventory'(params: { quantity: number }) {
     const { seedReservationInventory } =
       require('./cypress/support/purchase_order/reservation_helper');
     return await seedReservationInventory(params.quantity);
   },
   ```

Type-check before running: `npx tsc --noEmit -p cypress/tsconfig.json`.

## Interaction with `cleanup.py`

`npm run cleanup` only removes files it recognizes as generator output:
- generated specs/helpers are deleted (they're rewritten on the next
  `generate-code` anyway);
- **hand-written supplements are preserved** — they have no
  `AUTO-GENERATED` marker and a non-generated filename, so cleanup never
  touches them.

Keep the `_gen` suffix off your manual files and don't add the
`AUTO-GENERATED` marker to them, and your work is safe across regen/cleanup
cycles.
